# Contract 4: approve and deduplicate writes

No agent writes money, inventory or commitments on its own. A person approves
the exact terms; a policy caps the amount before the tool runs; a unique key
makes a retry find the first write; every executed call leaves one audit row.

## Template: the approval is a row the write references

The agent (Pellier's Planner) proposes one action and stops. The proposal is
inserted as a pending review with a hash of its exact arguments, so the same
proposal twice is one review, and a person approves *that* row:

```sql
CREATE TABLE approvals (
    id            bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id   text NOT NULL,
    tool          text NOT NULL,
    args          jsonb NOT NULL,
    action_hash   text NOT NULL,              -- hash of (tool, customer, amount, reason)
    status        text NOT NULL,              -- pending | approved | declined
    approved_by   text,
    approved_at   timestamptz
);
-- One live review per exact action: a second pending twin would be a second
-- card for one decision; a second approved twin would be a second key.
CREATE UNIQUE INDEX approvals_one_live_review
    ON approvals (customer_id, tool, action_hash)
    WHERE status IN ('pending', 'approved');
```

The idempotency key is derived from the approval, not minted per call:
`operator-review:<approval id>:<first 32 chars of action_hash>`. A caller
cannot invent a key that maps to an approval it does not have.

## Template: the write function

All the rules live in the database, so a direct SQL caller is held to them
too. Lock, then look for an existing row under the key, then check the
approval, then write. Simplified from Pellier's `apply_store_credit`:

```sql
CREATE TABLE store_credits (
    credit_id       bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    approval_id     bigint NOT NULL UNIQUE REFERENCES approvals (id),
    customer_id     text NOT NULL REFERENCES customers (id),
    amount_cents    integer NOT NULL CHECK (amount_cents BETWEEN 1 AND 50000),  -- safety ceiling in the schema
    reason          text NOT NULL,
    issued_by       text,
    idempotency_key text NOT NULL UNIQUE,
    created_at      timestamptz NOT NULL DEFAULT now()
);

CREATE FUNCTION apply_store_credit(p_key text, p_customer text, p_cents int, p_reason text, p_issued_by text)
RETURNS jsonb LANGUAGE plpgsql AS $$
DECLARE v_existing store_credits%ROWTYPE; v_review approvals%ROWTYPE;
BEGIN
    -- Serialise retries of the same approval: a concurrent replay waits here,
    -- then finds the first write.
    PERFORM 1 FROM approvals
     WHERE customer_id = p_customer AND tool = 'give_store_credit' AND status = 'approved'
       FOR UPDATE;

    SELECT * INTO v_existing FROM store_credits WHERE idempotency_key = p_key;
    IF FOUND THEN
        IF (v_existing.customer_id, v_existing.amount_cents, v_existing.reason)
           IS DISTINCT FROM (p_customer, p_cents, p_reason) THEN
            RETURN jsonb_build_object('status', 'idempotency_conflict');
        END IF;
        RETURN jsonb_build_object('status', 'success', 'replayed', true, 'credit_id', v_existing.credit_id);
    END IF;

    SELECT * INTO v_review FROM approvals
     WHERE status = 'approved' AND tool = 'give_store_credit'
       AND p_key = 'operator-review:' || id || ':' || left(action_hash, 32)
       AND args->>'customer_id' = p_customer
       AND (args->>'amount_cents')::int = p_cents
       AND args->>'reason' = p_reason;
    IF NOT FOUND THEN
        RETURN jsonb_build_object('status', 'approval_required', 'denied_by', 'approval_guard');
    END IF;

    INSERT INTO store_credits (approval_id, customer_id, amount_cents, reason, issued_by, idempotency_key)
    VALUES (v_review.id, p_customer, p_cents, p_reason, p_issued_by, p_key)
    RETURNING credit_id INTO v_existing.credit_id;
    RETURN jsonb_build_object('status', 'success', 'replayed', false, 'credit_id', v_existing.credit_id);
END $$;
```

Three guarantees, each by a different mechanism: *approved* by the review
lookup, *once* by the unique key plus the lock, *bounded* by the `CHECK`.

## Template: the policy limit at the gateway

A forbid wins over any permit. Write the limit as a forbid with a narrow
exception, and check the attribute exists before comparing it, so a request
with no amount stays forbidden:

```cedar
forbid(
  principal is AgentCore::OAuthUser,
  action == AgentCore::Action::"store-tools___give_store_credit",
  resource == AgentCore::Gateway::"<gateway arn>"
)
unless {
  context.input has amount_cents &&
  context.input.amount_cents <= 10000      // cents, inclusive
};
```

Test the matrix before deploying: the boundary (10000 allowed, 10001 denied),
a missing amount (denied), a shopper token (denied by the absence of any
permit), and the read tools still allowed. Pellier's check also confirms that
eight *wrong* rules (dollars instead of cents, `<` instead of `<=`, `true`)
are caught.

## Template: the audit ledger

```sql
CREATE TABLE tool_audit (
    audit_id          bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    session_id        text NOT NULL,     -- the turn id
    tool              text NOT NULL,
    caller            text NOT NULL,     -- the agent, 'gateway', or the staff member
    args              jsonb,
    result            jsonb,
    latency_ms        integer,
    build_fingerprint text,              -- which deployed build made the call
    created_at        timestamptz NOT NULL DEFAULT now()
);
-- Append-only: no UPDATE or DELETE grant to any application role.
```

One row per executed call. A denied call never reaches the tool, so it leaves
no row. A replay returns the first result and writes no row. Order by
`audit_id`, not `created_at`: `now()` is the transaction start time, so two
rows in one transaction share a timestamp.

## Three questions, three sources

| Question | Evidence | What it cannot tell you |
|---|---|---|
| Was it permitted? | The policy decision (ALLOW / DENY) | Whether anything ran |
| Did it run? | One `tool_audit` row for the key | What it wrote |
| Did state change? | One `store_credits` row for the same key | Why it was allowed |

An absence (0 audit rows, 0 credit rows for the denied key) is only evidence
beside a positive control (1 credit row for the allowed key, found by the same
query). Two zeros on their own could mean the query looked in the wrong place.

## Review questions

- Who approved this, what changed, and what proves it changed only once?
- Where is the key minted, and can a caller mint one without an approval?
- What would two concurrent retries do?
